# Задача

Реализовать экран:

```text
/events
```

для веб-приложения танцевальной платформы.

Экран предназначен для поиска и просмотра доступных танцевальных Ивентов.

Frontend:

```text
React
TypeScript
TanStack
```

Интерфейс должен полностью соответствовать визуальному стилю остального приложения.

Не создавать отдельную дизайн-систему специально для `/events`.

Использовать:

* существующие цвета;
* существующую typography;
* существующие кнопки;
* существующие карточки;
* существующие badges;
* существующие border radius;
* существующие spacing tokens;
* существующие layout-компоненты;
* существующий Header;
* существующую mobile navigation.

Если в приложении уже есть компоненты из Dashboard, переиспользовать их вместо создания визуально похожих дублей.

---

# 1. Назначение экрана

Экран `/events` является основным каталогом танцевальных мероприятий.

Пользователь должен иметь возможность:

* просматривать предстоящие Ивенты;
* искать Ивенты;
* фильтровать Ивенты;
* сортировать Ивенты;
* просматривать найденные Ивенты в виде списка/сетки;
* просматривать те же найденные Ивенты на карте;
* в любой момент переключаться между режимами `Список` и `Карта`;
* открывать страницу конкретного Ивента.

В MVP поддерживаются типы:

```text
Tournament
Master Class
```

В дальнейшем возможно добавление:

```text
Training Camp
```

Frontend не должен быть жестко привязан только к двум текущим типам.

---

# 2. Ключевое требование: два режима просмотра

Экран `/events` должен иметь два полноценных режима:

```text
Список
Карта
```

Они являются **двумя представлениями одного и того же набора результатов**.

Переключение между режимами:

* не должно сбрасывать поиск;
* не должно сбрасывать фильтры;
* не должно повторно инициализировать страницу с нуля;
* должно сохранять выбранный город;
* должно сохранять дату;
* должно сохранять направление;
* должно сохранять остальные фильтры;
* должно сохранять сортировку, где она применима.

Пример:

```text
Астана
Hip-Hop
Турниры
20–27 сентября
```

Пользователь нажимает:

```text
[Карта]
```

На карте должны отображаться именно Ивенты, соответствующие этим фильтрам.

После возврата:

```text
[Список]
```

должен отображаться тот же набор результатов.

---

# 3. Основной UX-принцип

Экран должен позволять быстро ответить на вопрос:

> Какие танцевальные мероприятия мне доступны в нужном городе, в нужную дату и по нужному направлению?

Основная модель:

```text
Поиск
   ↓
Фильтры
   ↓
Найденные Ивенты
   ↓
┌─────────────┐
│             │
Список      Карта
│             │
└─────────────┘
```

Режим просмотра не должен влиять на бизнес-результат поиска.

Ориентировочно:

```text

```

# 8. Search

Основное поле:

```text
Поиск по названию, организатору, городу или направлению
```

Поиск должен учитывать:

* название Ивента;
* организатора;
* город;
* направление.

Рекомендуемый debounce:

```text
300–500 ms
```

Поле должно иметь:

* search icon;
* clear button;
* responsive width.

# 23. Хранение режима в URL

Текущий режим должен храниться в search params:

```text
/events?view=list
```

или:

```text
/events?view=map
```

Это необходимо, чтобы:

* reload сохранял состояние;
* browser back/forward работал ожидаемо;
* ссылкой можно было поделиться.

# 30. Map markers

Каждый Event с:

```text
latitude
longitude
```

должен иметь marker.

Marker должен быть связан с соответствующим Event.

---

# 31. Marker → Event synchronization

При клике на marker:

1. Marker становится активным.
2. Соответствующая карточка в side list становится выделенной.
3. Если она вне viewport списка — список scroll-to-item.
4. На карте появляется компактный preview выбранного Ивента.

Пример:

```text
Kazakhstan Dance Open

25 сентября
Almaty

от 10 000 ₸

[Подробнее]
```

---

# 32. Event list → Marker synchronization

При наведении или выборе карточки в desktop map mode:

* соответствующий marker должен визуально выделяться.

При клике:

* центрировать карту на marker;
* открыть preview.

На mobile hover behavior не используется.

---

# 33. Selected Event state

Использовать отдельное UI state:

```ts
selectedEventId?: string;
```

Это UI-state, его не обязательно хранить в URL.

При переключении карты/списка selected Event можно сбросить.

---

# 34. Marker clustering

Если в одной области много Ивентов, использовать clustering, если map provider позволяет.

Например:

```text
[12]
```

При zoom-in кластер разделяется.

Не реализовывать собственный clustering algorithm, если он есть у map SDK.

---

# 35. Events без координат

Event без координат:

* должен оставаться в `Список`;
* может оставаться в side list map mode;
* не получает marker;
* не должен приводить к ошибке карты.

Допускается специальный indicator:

```text
Местоположение не указано
```

если это необходимо UX.

---

# 36. Map bounds

После получения результатов в map mode карта должна автоматически построить bounds, чтобы показать найденные markers.

Не делать чрезмерный zoom-out для географически очень удаленных Ивентов.

Если установлен фильтр города:

```text
Астана
```

центрировать карту на этом городе.

---

# 37. Geolocation

Не делать обязательный browser permission prompt при открытии `/events`.

Можно добавить:

```text
[Рядом со мной]
```

или использовать сохраненный город пользователя.

Если permission уже был предоставлен, можно использовать coordinates для первоначального центра.

---
